# Trusted method library

Each method here is **one R file** that follows a named upstream tutorial or
paper repository as closely as the app allows, plus **one entry** in
[`catalog.json`](catalog.json) describing its parameters, outputs, metrics,
provenance, and the results it may run on. Review a method once against its
upstream source. After that, people and agents reuse it by choosing parameters,
without writing or reviewing new code.

The same bytes serve both paths:

| Who | How it runs | Where |
| --- | --- | --- |
| People | Workflow packages generated by `npm run trusted-workflows:build`, imported under **Pipelines → Import workflow** | [workflow pipelines](../docs/workflow-pipelines.md) |
| Agents | One digest-pinned release per method (`trusted.method.v1`), approved per project and run inside a study | [agent automation](../docs/agent-automation.md#trusted-method-library) |

Both run in the isolated, no-network R sandbox. Neither path accepts R source
from the caller.

refuses a chain that a method's `accepts` list does not declare.

## The trust model, and the trade-off it makes

Flexibility and "no review needed" pull in opposite directions. The library
takes these positions:

1. **Code is fixed; data and settings vary.** An agent can choose only values
   inside a study a person defined. It cannot add a step, edit R, install a
   package, or reach the network. Changing a method's bytes changes its release
   digest and voids earlier approvals.
2. **Design choices are fixed by a person; tuning is searchable.** Every
   parameter has a `role`:
   - `design`: what the study asks, such as batch/sample columns, the gene list,
     the cluster→label mapping, or which cells to keep. These are set when the
     study is created and the server refuses to let an agent vary them
     (`PROTECTED_PARAMETER`).
   - `tuning`: numerical choices such as resolution, dimensions, integration
     method, or seed. An agent may search them within listed values.
   - `display`: figure-only settings.
3. **Text is data, never code.** Text parameters must match one of a few plain
   grammars (`genes`, `labels`, `labelMap`, `geneSets`, `column`). They are
   always `design` parameters, and the R method splits and re-checks them.
4. **Each step is accepted.** A method's result is a candidate until a person
   accepts it. Only accepted results can feed the next method, so a chain
   (doublets → subset → integrate → annotate) has a person's decision at every
   link. Standing auto-acceptance stays off.
5. **Deviations are declared.** Where a method must differ from its upstream
   code, for example joining Seurat v5 layers or splitting annotation from
   removal, the catalog's `deviations` list says so and approval shows it.

The trade-off: an agent cannot produce a figure or analysis that no method
covers. That case needs a proposal (inert text) and a reviewed new method, not
an ad hoc script. The library is meant to grow by one reviewed method at a time.

## Adding a method

1. Write `methods/<key>.R`. Use `inputs$analysis`, `params[["key"]]`, `seed`,
   and `write_output(name, value)` for every declared output, as in workflow
   packages. Cite the upstream section in comments next to the code it mirrors.
   The loader rejects shell, network, `eval`/`parse`, `source`, and package
   installation calls.
2. Add the catalog entry: provenance (URL, upstream file, citation, the version
   reviewed against), deviations, parameters with roles, outputs, a `metrics`
   output and the metric keys it promises (each with a `kind`: `descriptive`,
   `quality` or `inferential`; studies cannot rank trials by inferential
   metrics), resources, and `accepts`.
3. Run `npx vitest run backend/trusted-methods.test.js --environment node`.
4. If the method needs a package that is not in the R image, add it to
   `r-backend/Dockerfile` in the trusted-method layer. Methods fail with a
   clear message when a package is missing.

## Known gaps

- **Image-based data (Xenium, CosMx, MERFISH)** has no upload type yet. These
  methods work on such objects in the workbench (for example an uploaded Seurat
  RDS), but agents cannot start from them until a dataset type and release exist.
- **Two-input methods** are not supported by the job contract yet: label transfer
  or deconvolution from a separate single-cell reference (Seurat anchors, RCTD),
  and integration of a separately processed object.
- **Not covered:** RNA velocity (needs spliced/unspliced counts), CNV inference,
  TCR/BCR, ATAC/multiome, and GRN/regulon analysis. These are candidates for
  the next reviewed methods.

## Runtime requirements

Methods run through the [isolated R runtime](../docs/deployment.md#optional-expert-r-sandbox).
Running a library method does **not** need the `expert_r.execute` grant, because
no caller code runs. Some methods need packages beyond the base image, listed in
each catalog entry's `packages` field.
